## Domain model

### Nouns and ownership

**Domain (proposed):** a target use case in which a human judges Lane capability: coding, knowledge or automation. Choose a Class first; its Domain follows. A job has exactly one Class. Split independently verifiable deliverables into separate jobs when needed. This extends the Consultation §The classification abstraction / How to pick; it adds no classifier.

**Lane:** still one model, effort and harness. **Meter:** still the shared subscription observation. Neither duplicates when a Domain is enabled. (CONTEXT.md:22, CONTEXT.md:85.)

**Tier (proposed extension):** capability assigned to a Lane *within a Domain*. Keep the existing four-level scale. A knowledge Tier says nothing about browser availability. **Class (proposed extension):** a named kind of job bound to exactly one Domain. **Range:** its Floor through Ceiling in that Domain. **Order (proposed extension):** position inside that Domain's Tier. **Project order (proposed extension):** a project preference inside those global Domain Tiers. (Existing definitions: CONTEXT.md:51, CONTEXT.md:54, CONTEXT.md:58, CONTEXT.md:64, CONTEXT.md:76; Consultation §Target seams / Ranking rule and §Where the story is wrong or premature / Configurable tier count.)

**Domain availability (proposed):** whether setup offers that Domain for normal classification. **Assignment (proposed):** a Lane's recorded Tier for a Domain. Missing assignment means unassigned and ineligible there. It never means Tier zero or inheritance from coding.

### Proposed schema and deterministic behavior

- Proposed lane fields: 'tiers' maps known Domain names to a Tier; optional 'orders' maps those names to Order. Keep 'enabled' as global carry. Keep model, effort, harness, meter, price, timeout, published_as and basis. A basis entry should identify the Domain when it records new rationale. Do not store scores in the catalog.
- Proposed global routing field: 'domains' maps coding, knowledge and automation to booleans. Initially only coding is true. Proposed 'classes.<name>.domain' is global-only. Existing floor/ceiling stay beside it. Defined Classes remain in routing and the guide when their Domain is off.
- Proposed project field: 'project_orders.<domain>' is a flat list. Validate names, duplicates and global carry against the unprojected catalog. Also require an assignment in that Domain. Missing names follow that Domain's global Order. A project cannot enable a globally off Domain or change a Class's Domain.
- Preserve legacy 'project_order' as coding-only compatibility input. Reject a document containing both it and proposed 'project_orders.coding'. Never apply the old list to every Domain. This deliberately extends the dashboard's single-list decision because Tier membership can now differ by Domain. It remains one Order per Domain, never per Class. (Existing list decision: docs/superpowers/specs/2026-09-13-delegate-dashboard-plugin.md:90; Consultation §Target seams / Catalog on disk.)
- Proposed rank_range receives the resolved Domain. Proposed rank resolves it from the Class. Proposed tier_leaders requires the chosen Domain once several are available. All rows and printed headers identify the Domain. No cross-domain fallback is allowed.
- Preserve unknown-Meter-last, then Tier, ordered before unordered, Order, descending Pace, Lane name; preserve Margin steal and Gate equality. Those details come from the current code, not the older pseudocode. (agents/skills/delegate/scripts/rank.py:176, agents/skills/delegate/scripts/rank.py:205, agents/skills/delegate/scripts/rank.py:218; older spec: docs/superpowers/specs/2026-09-08-delegate-redesign.md:93; Consultation §Story to module map / Routing.)
- Proposed missing assignment is an explicit veto before Range checks. Reject unknown Domains, non-integer Tier/Order values and Orders without an assignment. Validate Tier bounds and positive Order using the existing rules. Reject null assignments; absence carries the unassigned meaning. Report a disabled Domain separately from an exhausted Range. Named dispatch retains its explicit escape from ranking; it gains no tool permissions. (Existing named-dispatch meaning: CONTEXT.md:80; Consultation §Open decisions for the maintainer / Named dispatch vs Gate.)
- Do not populate new Domain assignments by copying coding tiers. Preview candidate lanes and let the human assign them. Enabling a Domain requires a reviewed nonempty assignment set. Preview each affected Class for coverage; the human may retain an empty Range with a clear STOP outcome.
- Keep new schema writes behind a deliberate conversion. Proposed next-version tags distinguish the new shapes. A legacy read normalizes scalar tier/order to coding in memory only. Reject mixed scalar/map writes. Convert lanes and routing separately in an order that keeps each intermediate state readable; readers must support that transition before conversion ships.

### Tools and authority are separate from Class

The current skill says '--write' enables shell work and edits. Actual prompt construction gives agy a read-only sandboxed terminal clause, and relay arguments differ by harness. A Class must not promise shell or browser access merely because ranking found a CLI. (agents/skills/delegate/SKILL.md:28; agents/skills/delegate/scripts/delegate.py:305, agents/skills/delegate/scripts/delegate.py:310, agents/skills/delegate/scripts/delegate.py:440; agents/skills/delegate/scripts/rank.py:180.)

- scout, review and knowledge classes can use read tools. A browser is needed only when the brief needs web or application evidence. A shell may be needed for verification or artifact production. File production requires an existing authorized '--write' directory.
- mechanical, impl and hard-impl commonly need shell and file writes. automation-inspect needs the relevant browser/API/shell read interface. automation-execute and automation-recover need the interface the procedure names. Classifying alone grants none of these.
- The worker preamble permits writes in a Disposable browser and forbids all other network writes. '--write' grants local writes only. Therefore production SaaS mutation, sending messages, publishing and trading are outside this scope. Real-system automation requires a separately designed authorization change; tier work must not smuggle it in. (agents/skills/delegate/assets/preamble.md:1; agents/skills/delegate/scripts/delegate.py:305; CONTEXT.md:125.)
- A proposed setup preview must display browser/shell probe evidence and whether it matches the harness, machine and run mode. Missing evidence remains “unknown.” Before an automation run, the orchestrator verifies a compatible path or stops. Do not misuse '--harnesses' as a capability filter. (Existing constraint guidance: agents/skills/delegate/SKILL.md:36; existing probe evidence requirement: agents/skills/delegate/SKILL.md:56.)
- Keep the existing leash behavior for coding. Proposed new Classes keep the conservative leash by default; the orchestrator may choose the existing '--no-leash' for a bounded long job. Do not infer leash policy from a domain name. (agents/skills/delegate/scripts/delegate.py:264; Consultation §The classification abstraction / How to pick.)

## The judgment wizard

### Interaction contract

Proposed default for “setup, change X”: the orchestrator gathers facts, presents one concrete choice and its effect, records the human's decision, and invokes a plain CLI writer. A statement such as “use Astra more” authorizes preparing alternatives; it does not identify a Tier or Range to write. In a non-interactive run, return a proposal and unresolved choices without applying guessed policy.

Use existing '/delegate setup' as the entry point. Proposed skill prose routes a surgical request to the verbs below; an unspecified first setup can still open the TUI. Do not create a second setup skill or a Python classifier. (agents/skills/delegate/SKILL.md:18; Consultation §Setup as a re-runnable, surgical operation and §Where the story is wrong or premature / /delegate-setup as a second skill.)

**Proposed common write protocol:** show the real target file, global value, effective project value, changed fields and affected Class Picks. Use the same cached Meter snapshot for before/after. Identify missing observations. Require a human-selected value, validate the complete proposal, detect intervening file changes, then write only the selected document in its explicit global or project scope. Reload through load_catalog and show the result. A prior explicit decision is enough; do not ask twice.

Existing setup reads editable global files directly; catalog.load_catalog provides the effective project view. Proposed previews must show both and must never serialize projected project Order into a global file. Existing writes are atomic per file, not a transaction across both files. Resolve and show stow targets before writing; do not replace the symlink. (agents/skills/delegate/scripts/setup.py:72, agents/skills/delegate/scripts/catalog.py:769, agents/skills/delegate/scripts/catalog.py:103, agents/skills/delegate/scripts/setup.py:375; agents/skills/delegate/CLAUDE.md:23; Consultation §Target seams / Catalog on disk.)

## Risks and pushback

- **A third Domain may arrive before its evidence.** The notes support API workflows and terminal work, not installed GUI competence. Alternative: ship coding-only verbs, then knowledge, and keep automation off until bounded examples exist. (AA §AutomationBench; Web §Terminal-Bench v4.0 and §APEX-Agents; Consultation §Where the story is wrong or premature / Benchmarks assign tiers.)
- **Knowledge is internally uneven.** Omniscience and GDPval reverse Astra/Opus high. Do not create finance, investing and engineering sub-axes without evidence. Alternative: one knowledge Tier, good Class boundaries, and explicit named dispatch when necessary. (AA §Omniscience, Models of interest, lines 116 and 141; §GDPval, Models of interest, lines 322 and 347.)
- **“Higher Tier” can mean less use.** Tier is capability, Order is preference, and Range is eligibility. A setup that treats them as one slider will mislead. Alternative: show the actual affected Pick before writing. (agents/skills/delegate/scripts/rank.py:172, agents/skills/delegate/scripts/rank.py:205, agents/skills/delegate/scripts/rank.py:263.)
- **An all-board mean obscures the decision.** Scores have different meanings and source costs differ. Alternative: show per-board evidence and let the human explain the assignment. Keep source-scoped carry arithmetic unchanged. (AA §Source and §GDPval; Web §DeepSWE; agents/skills/delegate/scripts/setup_tui.py:430; Consultation §Target seams / Benchmark decisions.)
- **Global carry can erase a specialist Lane.** The current carry proposal considers a source-wide majority across shared boards. It is not a per-domain conclusion. Alternative: preserve global carry, show affected Domains, and require explicit review. A domain-specific carry algorithm is outside this scope. (agents/skills/delegate/scripts/setup_tui.py:430, agents/skills/delegate/scripts/setup_tui.py:494.)
- **Instant add-class overpromises.** Names are consumed in several modules and affect prompts. Alternative: a generated development proposal, followed by tests and guide review. Reconsider an open registry only after actual class additions show enough friction. (agents/skills/delegate/scripts/catalog.py:51, agents/skills/delegate/scripts/delegate.py:181, agents/skills/delegate/scripts/delegate.py:264, agents/skills/delegate/scripts/setup_tui.py:1111; Consultation §Open decisions for the maintainer / Closed CLASSES tuple vs open names.)
- **Replacing the TUI adds a frontend project.** Surgical CLI plus orchestrator prose removes the full-pass burden without rebuilding every setup interaction. Keep the HTML page as evidence and drafts. Retire the TUI only after these verbs cover real use. (Consultation §Setup as a re-runnable, surgical operation / Three verbs and §Where the story is wrong or premature / HTML as the setup UI.)
- **Permissions can be mistaken for capability.** A high automation Tier cannot override the no-network-writes preamble or establish working browser access. Alternative: explicit run-mode evidence and a separate future authorization design. (agents/skills/delegate/assets/preamble.md:1; agents/skills/delegate/SKILL.md:56.)
- **More schema means more maintenance.** Domain-scoped Order and draft storage are necessary costs of independent tiers. Separate catalogs would add duplication too. Alternative: stop after M5 if the human does not actually make differing domain assignments.
- **Historical reports and project policies need compatibility.** Class-to-Domain bindings must remain stable; do not reinterpret old runs through current Lane tiers. Preserve legacy coding projection and show missing historical context as unknown. (agents/skills/delegate/scripts/report.py:648; agents/skills/delegate/scripts/catalog.py:727; Consultation §Target seams / Catalog on disk.)

## Decisions for the maintainer

1. **One capability axis or per-domain assignments?** Recommend per-domain tiers as the target, with coding-only surgical verbs delivered first. Separate catalogs lose the single authoritative Lane record.
2. **Enable knowledge and automation together?** Recommend reviewing knowledge first. Define automation Classes now, but keep their Domain off until disposable/local workflows provide evidence.
3. **One Order everywhere or per Domain?** Recommend per-domain global Order and project lists. Interpret legacy project_order as coding-only. This is an explicit revision of the dashboard's original one-list assumption.
4. **Immediate add-class or a reviewed development change?** Recommend the closed registry plus a proposed class-proposal verb. Keep name, guide, Range, dispatch behavior and tests coordinated.
5. **Replace the TUI now or make it optional?** Recommend optional TUI for full review; plain CLI plus orchestrator prompts for surgery; HTML for evidence and drafts; Herdr for project observation and supported controls.
6. **Recalculate carry per Domain or retain the settled rule?** Recommend retaining the arithmetic. Make proposals visible, preserve current decisions during surgery, and require explicit approval for global carry changes affecting several Domains.
